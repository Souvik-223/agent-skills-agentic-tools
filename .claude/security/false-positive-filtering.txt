## SECURACY.AI — FALSE POSITIVE FILTERING INSTRUCTIONS
## Stack: Python/FastAPI backend, Vue.js frontend, RAG pipeline (CAPEC/CWE), MCP server

---

HARD EXCLUSIONS

1. All default exclusions from the base security-review command apply (DOS, rate limiting, resource exhaustion, etc.)
2. FastAPI automatic input validation via Pydantic models — do NOT flag missing manual validation when Pydantic schemas handle it.
3. Vue.js template bindings (v-bind, {{ }}) — Vue escapes by default. Only flag v-html usage.
4. MCP server tool definitions themselves — tool parameter schemas are not attack surfaces from untrusted users unless the MCP is exposed publicly.
5. Python type hints and Pydantic field constraints — these are validation, not security issues.
6. CAPEC/CWE database read operations — these are reference data lookups, not user-controlled injection points.
7. Internal RAG pipeline prompts — including user context in RAG prompts is by design and is not prompt injection unless untrusted external content is injected without sanitization.
8. Environment-based configuration (API keys via .env/os.environ) — these are assumed secured at infrastructure level.
9. Async def endpoints without explicit rate limiting — rate limiting is handled at infrastructure/API gateway level.
10. CORS configuration during development — only flag if CORS is wildcard in a file clearly marked for production.

---

SIGNAL QUALITY CRITERIA (Securacy-specific additions)

1. FastAPI dependency injection: Is the vulnerability in an actual dependency function, or just the schema definition?
2. RAG pipeline: Can the untrusted input actually reach the vector store write path, or only the read/query path?
3. Threat model output: Securacy generates structured JSON threat models — is the vulnerability in the generation logic or just the output format?
4. MCP server: Is the tool callable from an unauthenticated external source, or only via the Claude Desktop integration?
5. Vue.js: Is the finding in a component that renders user-generated content, or internal application state?

---

PRECEDENTS (Securacy-specific)

1. CAPEC/CWE IDs are not user-controlled injection vectors — they are validated identifiers from a curated database.
2. Architecture description inputs from users ARE untrusted and MUST be treated as potentially adversarial in the threat analysis pipeline.
3. JSON threat model outputs do not need HTML escaping unless they are rendered directly in HTML without a framework.
4. Python `subprocess` calls are expected for running validation scripts (.claude/scripts/) — only flag if they incorporate unsanitized user input directly.
5. Logging threat analysis results (CAPEC/CWE matches, severity scores) is safe and not PII — do not flag.
6. UUIDs used as session/analysis identifiers are assumed unguessable.
7. FastAPI OAuth2/JWT dependencies are assumed correctly configured — only flag if there is a concrete bypass in the actual implementation code.
